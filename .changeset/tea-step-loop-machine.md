"@demlik/tea": minor

`runStepLoop` (`@demlik/tea/do`) runs its decisions as a tea machine on `run`: when to POST, what a response means, when to run a step, retry, back off, give up, stop at the deadline or finish. The clock, the transport, the hands and the sleep are its Cmds. `@demlik/tea/do` exports the machine, `stepLoopMachine<R, I, O>()`, and its `StepLoopState`, `StepLoopMsg` and `StepLoopCmd` types, and `RunStepLoopConfig` takes `attach(runtime)`, called once with the drive's runtime before it boots. `recorder(runtime, { captureSteps: true })` then records a drive, and `replayTrace(stepLoopMachine(), trace)` (or `replayStoredTrace` for a recording read back from JSONL) replays it. The recorded Msgs carry the values each decision read: every clock read, each response, each failure and whether `retryable` allowed it, the result that was posted, and each sleep. The signature, the outcomes, the order of calls and the number of clock reads are unchanged. The machine decides on exactly the numbers you pass, and the recorded `start` Msg carries them. JSON has no `NaN` or `Infinity`, so a `deadlineMs` or a `retry` number that is `NaN` or infinite replays from the dumped trace, but may not replay from the text `toJSONL` wrote, which reads it back as `null` (`maxAttempts` of `NaN` or `Infinity` does not; a `NaN` deadline and a `NaN` `maxElapsedMs` happen to); `deadlineMs: Infinity` is the exception, because the machine holds it as `null`, "no deadline". Write a retry policy with no limit as `unbounded: true`, not as an infinite `maxAttempts` or `maxElapsedMs`.

**Additive (declaration only):** four new names, `stepLoopMachine`, `StepLoopState`, `StepLoopMsg` and `StepLoopCmd`. `RunStepLoopConfig` gains the optional `attach` and two type parameters, `I` and `O`, that default to `never`.

**Breaking:** two behaviours change.

- Where tea's dev checks run (`NODE_ENV` is not `production`), the machine's State is deep-frozen before each reducer step, and the State now holds what the drive was handed: the result `execute` returned, a step's `input` once its result is posted, a failure that is a plain object, and the `config.retry` object (the shared `defaultRetryPolicy` from `retry-backoff`, process-wide, when you omit it). A caller that mutates one throws a `TypeError` where the loop it replaced let it. An `execute` that returns a shared accumulator and changes it on the next call rejects the drive, and so does pushing onto a returned result after the drive. Return a fresh value from `execute`. `done`'s `output` is not frozen, and a production build freezes nothing.
- A drive is now one `dispatch`, and tea ends a `dispatch` that has run 100,000 follow-up Msgs with `QuiescenceTimeoutError`. The count runs over the whole drive: 3 Msgs for the start and the final answer, 3 for each step, 4 for each not-ready poll, and 3 for each failed POST that is retried (the failure, its clock read and its sleep). That is a drive of about 33,000 steps, or 25,000 not-ready polls, or a mix, where the loop it replaced had no bound. A caller that drives longer starts another `runStepLoop` with the same `executed` store, which does not run the steps it already ran.
