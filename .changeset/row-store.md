Add the experimental `rowStore(port, { parse, encode, fenced: true })` on `@demlik/tea/persistence`, with the `RowPort` and `RowStoreOptions` types. It is a fenced, deletable `Store` over one SQL row. tea imports no SQL library: the host binds a four-method `RowPort` (`read`, `insert`, `update`, `remove`) to its table and row id. State lives in the row's own columns through the host's `parse`, which answers the State or `refuse(reason)` and never `null`, and `encode`; the fence is the row's revision, and `saveFenced(state, n)` writes revision `n + 1` or throws `StoreConflictError` carrying both versions, where `actualVersion` is the revision a diagnostic read saw after the refusal. A port bound to the host's transaction makes the save part of it. With `boot: "restored"`, for an existing row, when `init` returns the loaded State itself (`Object.is`), no Subs or Cmd follow-ups dispatch additional messages, and storage succeeds, a one-Msg request costs one read and zero writes for a no-cell refusal, or one read and one write for an accepted transition. Birth and a changed State from init add a boot write. A failed save can add diagnostic reads and a final save attempt at stop. On a wake, restored init's Cmds do not run; on a birth, with nothing loaded, init's Cmds run. An insert always writes revision 1, so a row re-created after `delete()` starts again at revision 1. There is no unfenced form, and no log: a machine keeps pending work in its State.
